Chapter 07

데이터패스와 실행 유닛

이슈 큐가 명령어를 골랐다고 바로 계산이 시작되지는 않는다. 피연산자 값을 어딘가에서 읽어 와야 하고, 결과를 다시 어딘가에 써야 한다. 이 장은 KMHv3가 값을 읽고, 계산하고, 쓰는 경로를 따라간다. 레지스터 파일 포트, OG0·OG1 두 읽기 단계, 바이패스와 레지스터 캐시, FU 지연 표, 라이트백 중재, SRT16 나눗셈기까지 다루며, 이슈 선택과 웨이크업은 6장, 로드 유닛은 9장, 커밋은 8장에 맡긴다.

  • 레지스터 파일 포트가 왜 비싼지 설명하고, KMHv3가 포트 12개를 25개 소스에 나눠 주는 방식을 읽을 수 있다.
  • OG0와 OG1에서 uop가 실패하는 조건을 코드 줄과 함께 말할 수 있다.
  • 뱅크 충돌과 OldestArbiter의 우선순위 갱신을 손으로 계산할 수 있다.
  • forward, bypass, 레지스터 캐시, 레지스터 파일 가운데 어떤 경로로 값이 오는지 예측할 수 있다.
  • 고정 지연과 가변 지연 FU가 라이트백 포트를 다르게 다루는 이유를 설명할 수 있다.
  • SRT16 나눗셈기의 사이클 수를 피연산자 비트 수로 계산할 수 있다.

레지스터 파일: 포트가 왜 비싼가

식당 주방을 떠올려 보자. 요리사 열여섯 명이 한 냉장고에서 재료를 꺼낸다. 냉장고 문이 하나뿐이면 줄을 서야 한다. 문을 열여섯 개 달면 줄은 사라지지만 냉장고가 커지고 비싸진다. CPU의 레지스터 파일register file, RF이 바로 이 냉장고이고, 문이 포트port이다.

KMHv3의 정수 스케줄러에는 실행 유닛(EXU) 16개가 있다. ALU 6개와 BJU 3개는 소스 2개씩, LDU 3개, STA 2개, STD 2개는 정수 소스 1개씩 읽는다. 모두 합하면 한 사이클에 정수 소스 25개를 읽을 수 있어야 한다(intSchdParams, Parameters.scala:340-452에서 센 값). 정수 물리 레지스터는 224개이다(Parameters.scala:121-126).

면적만 문제가 아니다. 선이 길어지면 읽기가 느려지고, 그만큼 클록을 올리기 어렵다. 그래서 KMHv3는 소스마다 포트를 따로 주지 않고 읽기 포트 12개를 25개 소스가 나눠 쓴다. 각 소스는 설정에서 IntRD(포트, 우선순위)로 자기 포트를 정해 둔다. 포트 수는 getIntRfReadSize가 서로 다른 포트 번호를 세어 정한다(BackendParams.scala:425-433). 쓰기 포트는 IntWB 번호 0..8의 9개이다. 아래 표는 Parameters.scala:340-452를 손으로 센 것이다. 생성된 RTL로는 확인하지 못했으므로 포트 수 12와 9는 (추론)으로 둔다.

표를 보면 한 포트에 ALU 소스와 BJU·STD·STA·LDU 소스가 섞여 있다. 같은 사이클에 모두가 RF를 읽지는 않는다. 많은 소스가 바이패스나 레지스터 캐시, 즉치값으로 채워진다(4절). 그러니 포트를 나눠 써도 충돌은 가끔만 생긴다. 충돌이 생기면 진 쪽이 OG0에서 실패하고 다시 발행된다(2절).

이슈에서 실행까지: OG0와 OG1

포트를 나눠 쓰면 누가 이번 사이클에 포트를 쓸지 정해야 한다. 이 결정과 실제 읽기를 같은 사이클에 하면 너무 느리다. KMHv3는 이슈 큐(IQ)에서 고른 뒤 OG0·OG1operand generation이라는 두 단계를 거쳐 실행 유닛에 도착한다.

RF 자체도 주소를 레지스터에 담고 다음 사이클에 값을 낸다(thisBank(RegNext(r.addr(i))), Regfile.scala:182). 그래서 OG0에서 주소를 내면 OG1에서 값이 나온다. OG1의 끝에는 BypassNetwork가 있어서 RF 값과 다른 원천 가운데 하나를 고른 뒤 EXU 입력 레지스터에 넣는다(Region.scala:500-524). OG0를 통과하는 조건은 한 줄이다.

뱅크와 읽기 포트 중재

포트 7은 LDU0, ALU3의 두 번째 소스, BJU0의 두 번째 소스가 함께 쓴다. 셋이 같은 사이클에 RF를 읽으려 하면 둘은 진다. 이 충돌을 줄이려고 KMHv3는 정수 RF를 뱅크bank 4개로 나눴다(numBank = 4, Parameters.scala:123).

뱅크 번호는 물리 레지스터 번호의 하위 비트이다(bankIndex = addr(bankRaddrWidth-1, 0), PregParams.scala:22-25). 나머지 상위 비트가 뱅크 안의 주소이다(:27-30). 읽기 포트 하나는 뱅크마다 하위 포트를 하나씩 가지므로(r.data(i) := thisBank(...), Regfile.scala:182), 같은 포트를 쓰더라도 뱅크가 다르면 동시에 읽힌다. 뱅크 수는 1, 2, 4만 허용된다(Regfile.scala:95, :450).

2026-08-17 뱅크 번호를 하위 비트로 (#6357)

처음 4뱅크 분할(커밋 5aac7300a, 2025-12-25)은 상위 비트를 뱅크 번호로 썼다. 커밋 메시지는 두 문제를 적었다. 뱅크 크기가 고르지 않았고, 마지막 뱅크에 엔트리가 하나도 없으면 컴파일 오류가 났다. 하위 비트를 쓰면 224개가 56개씩 고르게 나뉜다. 메시지는 다음 설계로 PTAG = IndexInBank ## BankIndex를 예고한다.

바이패스 네트워크와 레지스터 캐시

ALU 결과를 RF에 쓰고 다시 읽으려면 몇 사이클이 걸린다. 그동안 의존하는 명령어가 기다리면 a = b + c; d = a + 1 같은 흔한 연쇄가 느려진다. 해결책은 결과를 RF를 거치지 않고 다음 명령어 입력으로 바로 넘기는 것이다. 이것이 바이패스bypass, forwarding이다.

어느 원천을 쓸지는 uop가 IQ에 있을 때 이미 정해 둔다. 이 4비트 값이 dataSource이다. 디스패치 때 psrc가 0이면 zero, 즉치면 imm, 나머지는 reg로 시작한다(IssueQueue.scala:320-323). 웨이크업을 받으면 bypass나 forward로 바뀌고, 한 사이클 뒤에는 다시 reg나 regcache로 돌아간다(EntryBundles.scala:401-402, :505-511).

확인 퀴즈

  

    
ALU3이 psrc 6(src0)과 psrc 14(src1)를 읽는다. 같은 사이클에 STA0이 psrc 10을, LDU0이 psrc 18을 읽는다. 셋 다 RF에서 읽는다면 ALU3은 어떻게 되는가? (두 사이클 전에는 요청이 없었다)

    

    
src0(6, 하위 10 → 뱅크 2)은 포트 6에서 STA0(10, 뱅크 2)과 부딪히지만 ALU3 src0이 우선순위 0이라 이긴다. 그래서 둘째 보기는 틀리다. src1(14, 뱅크 2)은 포트 7에서 LDU0(18, 뱅크 2)과 부딪히고 LDU0이 우선순위 0이다. 요청이 없던 상태에서는 입력 순서가 우선순위이므로 ALU3이 지고, 소스 하나라도 지면 uop 전체가 실패한다(G7-4). 첫째와 넷째 보기는 포트 7의 뱅크 충돌을 놓쳤다.

  

  

    
ALU 생산자 P가 t에 선택되고, 의존하는 소비자 C가 t+2에 선택되었다. C는 값을 어디서 받는가?

    

    
가장 이른 C 선택은 t+1이고 그때가 forward이다. 한 사이클 늦은 t+2면 C의 OG1(t+4)에서 P의 결과(t+3)는 레지스터에 한 번 담긴 bypass 값이다. forward는 k=0일 때, RF나 RC는 k≥2일 때이다. bypass2는 벡터 전용이다(BypassNetwork.scala:126-142).

  

  

    
ALU4에서 t에 MUL을 발행했다. busy table이 ALU 발행을 막는 사이클은?

    

    
MUL(지연 2)을 발행하면 다음 사이클 표의 비트 1이 서고(t+1, 지연 1 FU가 없으므로 아무것도 막지 않는다), 그 다음 사이클 비트 0이 선다(t+2). 비트 0은 지연 0인 ALU를 막는다. 두 FU는 출력 포트를 공유하므로 셋째 보기는 틀리다. t+3에는 표가 이미 비었다.

  

  

    
64비트 나눗셈에서 |피제수| = 2^40 이상(41비트), |제수| = 2^10 이상(11비트)이다. 결과는 입력 수락 후 몇 사이클에 나오는가?

    

    
aLZC = 23, dLZC = 53, 차이 30이다. N = (30+1)>>2 = 7이고 결과는 N+6 = 13이다. 12는 +6 대신 +5로 센 값이다. 5는 특수 경우이고, 36은 차이를 4로 나누지 않고 그대로 더한 값이다.

  






  
핵심 정리

  
    
    
  • 정수 RF는 224개, 4뱅크이고 읽기 포트 12개를 25개 소스가 나눠 쓴다. 포트와 뱅크가 같을 때만 충돌한다.
    • 
    
  • uop는 선택 → OG0(중재) → OG1(데이터, 바이패스 선택) → EX 순서로 간다. 소스 하나라도 지면 OG0에서 uop 전체가 실패한다.
    • 
    
  • OldestArbiter는 두 사이클 전 요청의 robIdx로 우선순위를 다시 매겨 오래된 uop를 먼저 보낸다.
    • 
    
  • 값의 원천은 생산자와의 거리로 정한다. 거리 0이면 forward, 1이면 bypass, 그보다 멀면 RC 또는 RF이다. RC는 RF 포트 압력을 덜어 준다.
    • 
    
  • 고정 지연 결과는 busy table로 쓰기 사이클을 예약하고, 가변 지연 결과는 중재에서 이길 때까지 기다린다. 그 가운데 Csr, Div, Fdiv, Vfdiv만 결과 3사이클 전에 미리 알린다(FuConfig.scala:867-869).
    • 
    
  • SRT16 나눗셈은 LZC 차이로 반복 수를 정하며, 결과는 N+6사이클(최대 21), 특수 경우 5사이클에 나온다.
