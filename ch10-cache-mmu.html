Chapter 10

캐시, TLB, 프리페처

9장에서 load는 주소를 계산해 DCache에 "이 주소의 값을 달라"고 물었다. 그 질문은 수십 사이클 걸릴 수도, 한 사이클 만에 끝날 수도 있다. 차이를 만드는 것이 캐시 계층, 주소 번역(TLB), 그리고 미리 가져오기(프리페처)다. 이 장에서는 L1 데이터 캐시(DCache), L1·L2 TLB, L1 프리페처를 코드 줄 단위로 다루고, L2(CoupledL2)·L3(OpenLLC)는 내부 소스가 이 체크아웃에 없어 연결 파라미터만 다룬다.

  • 캐시를 여러 층으로 쌓는 이유를 지연과 용량의 맞바꿈으로 설명하고 AMAT를 계산할 수 있다.
  • KMHv3 DCache 주소를 offset·bank·set·tag로 나누고, 해시 set index와 alias가 왜 생기는지 설명할 수 있다.
  • hit, bank conflict, MSHR merge/reject, write-back, PLRU 교체 규칙이 각각 무엇을 막는지 말할 수 있다.
  • 48엔트리 L1 TLB와 L2TLB 페이지 워크(Sv39/Sv48)를 따라가고 A/D 비트가 page fault가 되는 조건을 예측할 수 있다.
  • Stride·Stream·SMS 프리페처가 언제 요청을 내는지 실제 문턱값으로 예측할 수 있다.

왜 캐시를 여러 층으로 쌓는가

책상 위 메모는 손만 뻗으면 읽지만 몇 장밖에 못 둔다. 책장은 더 많이 들어가지만 일어나야 하고, 도서관은 무엇이든 있지만 오가는 데 한참 걸린다. 메모리도 같다. SRAM은 클수록 선이 길어지고 비교할 칸이 늘어 느려진다. 그래서 작고 빠른 층을 코어 가까이, 크고 느린 층을 뒤에 둔다. 이것이 캐시 계층(cache hierarchy)이다.

캐시와 메모리는 바이트 하나가 아니라 64바이트 묶음인 캐시 라인(cache line) 단위로 오간다. 한 바이트를 읽으면 그 이웃도 곧 읽힐 가능성이 높다는 공간 지역성을 이용한다. 찾는 라인이 있으면 hit, 없으면 miss이고, miss면 아래 층에서 가져와(refill) 채운다.

층 (구현)용량wayset (bank당)
L1D (DCache)64KB4256
L2 (CoupledL2)2MB81024
L3 (OpenLLC)32MB168192

set 수는 용량 / bank 수 / way / 64B로 계산했다. L1D 64·1024/4/64 = 256 (Configs.scala:300, 587), L2 2MB/4/8/64 = 1024 (:323, 339, 586), L3 32MB/4/16/64 = 8192 (:382, 584). L3 기본값은 OpenLLC다(system/SoC.scala:84). Configs.scala의 경로 접두는 src/main/scala/top/이다. 각 층이 hit에 몇 사이클 걸리는지는 이 저장소에 없다. L2와 L3 파이프라인은 git 서브모듈(XSCache, 핀 300515bc) 안에 있고, 이 체크아웃에서는 서브모듈이 비어 있다. 그래서 아래 계산기의 지연값은 모두 가정이며 독자가 바꿀 수 있게 두었다.

주소를 자르는 법: offset, set, way, tag

캐시는 거대한 사물함과 같다. 사물함 줄(set(set))은 주소의 일부로 정해지고, 한 줄에는 칸(way)이 4개 있다. 주소를 세 조각으로 자르면 된다. 맨 아래 offset은 라인 안의 바이트 위치, 그 위 index는 몇 번째 set인지, 나머지 위쪽 비트인 tag는 "이 칸의 라인이 정말 내 주소인가"를 비교하는 이름표다.

KMHv3 DCache의 실제 숫자로 해 보자. 라인이 64B이므로 offset은 6비트다(DCacheSetOffset = 1 + log2(32) = 6, DCacheWrapper.scala:190). set이 256개이므로 index는 8비트다. 데이터 배열은 2바이트 폭 bank 32개로 나뉘어 있고 bank 번호는 vaddr[5:1]이다(addr_to_dcache_bank, DCacheWrapper.scala:255-258). tag는 물리주소 paddr[47:12], 36비트다(tagBits = 48 − 12, L1Cache.scala:56, 93).

여기서 문제가 하나 생긴다. load가 s0에서 가진 것은 가상주소뿐이고 물리주소는 TLB가 한 사이클 뒤에 준다. 그래서 index는 가상주소로, tag는 물리주소로 비교한다. 이것을 VIPT(virtually indexed, physically tagged)라 한다. 4KB 페이지 안쪽 12비트는 가상·물리주소가 같지만, 256 set × 64B = 16KB라 index가 페이지 밖 2비트를 더 쓴다. 같은 물리 라인을 가리키는 두 가상주소가 이 2비트에서 달라지면 같은 라인이 서로 다른 set 두 곳에 들어갈 수 있다. 이것이 alias다.

set의 위쪽 2비트는 그냥 vaddr[13:12]를 써도 된다. 실제로 예전 방식(modeId = 2)이 그랬다. 하지만 16KB 간격으로 정렬된 배열 여러 개를 함께 훑으면 모두 같은 set에 몰린다. 4-way set에 5번째 배열이 들어오면 매번 누군가 쫓겨난다. 지금 기본(modeId = 1, L1Cache.scala:81)은 vaddr[47:12]를 2비트씩 잘라 18쌍을 XOR한다. 위쪽 비트가 다른 배열은 다른 set으로 흩어진다. 같은 2비트가 alias 값이 되어 miss 요청에 실려 L2로 간다(MissQueue.scala:304). L2는 L1D 클라이언트 설정의 aliasBitsOpt(Configs.scala:349)로 이를 받아 alias를 정리한다. 정리 방법 자체는 L2 소스가 없어 확인하지 못했다(추론).

bank conflict: 한 사이클에 load 셋이 같은 bank를 원할 때

bank 하나는 단일 포트 SRAM이고, 한 행에 같은 set의 4 way를 모두 담는다(packedRowBits = DCacheWays × encDataBits, BankedDataArray.scala:181). 8B 스칼라 load는 bank 4개(DCacheWordBankCount = 8/2), 16B 벡터 load는 8개를 읽는다(DCacheVWordBankCount = 128/16, DCacheWrapper.scala:183-184). 두 load가 같은 bank를 원해도 같은 set이면 같은 행을 함께 읽으므로 괜찮다. 다른 set이면 한 포트로 두 행을 읽을 수 없다.

miss와 MSHR: 기다리는 동안 다른 일을 한다

식당 주방에 주문서 꽂이가 있다고 하자. 재료가 떨어진 주문은 꽂이에 꽂아 두고 다음 주문을 받는다. 재료가 오면 꽂이에서 주문서를 빼 요리를 마저 한다. 이 꽂이 한 칸이 MSHR(Miss Status Holding Register)이다. KMHv3 DCache의 MissQueue에는 MissEntry가 16개 있다(nMissEntries = 16, Configs.scala:308; MissQueue.scala:1242).

순서는 이렇다. MSHR을 할당하고 A 채널로 AcquireBlock(데이터가 필요할 때) 또는 AcquirePerm(store가 라인 전체를 덮어쓸 때)을 보낸다(MissQueue.scala:290-302). D 채널로 Grant가 2 beat 오면 E 채널로 GrantAck를 보내고, MainPipe에 refill을 맡긴다. MainPipe가 tag·meta·data를 기록하고 응답하면 칸이 풀린다(release_entry = s_grantack && w_mainpipe_resp && w_refill_resp, MissQueue.scala:587). L1과 L2 사이에는 채널이 2개 있고, MSHR마다 paddr[6]로 채널을 고정해 A·D·E가 같은 길로 다닌다(MissQueue.scala:549-557; 2026-07-22 06f4a7404, #6178).

쓰기, 교체, 일관성

store는 9장에서 본 Sbuffer에 모였다가 DCache MainPipe로 들어온다(MainPipe.scala:261-262). tag·일관성 상태·데이터를 쓰는 파이프는 MainPipe뿐이다. LoadPipe s3는 접근 표시와 프리페치 표시 비트만 고친다(LoadPipe.scala:577, 586). 들어오는 요청은 고정 우선순위로 고른다. probe > refill > prefetch > store > atomic(MainPipe.scala:282-292; chisel Arbiter는 앞 번호 우선, mem/MemBlock.scala:85-95). L2가 회수하려는 라인(probe)을 먼저 처리해야 다른 코어가 기다리지 않고, 도착한 데이터(refill)를 먼저 넣어야 MSHR이 풀린다.

KMHv3 L1D는 write-back(write-back) 캐시다. store hit은 데이터만 고치고 상태를 Dirty로 둔다. 라인이 쫓겨날 때 Dirty면 ReleaseData로 L2에 내려 보낸다(need_wb = miss_wb || probe_wb || replace_wb, MainPipe.scala:812-815). WritebackQueue는 18칸이다(Configs.scala:310).

일관성: 사본이 여럿일 때

코어마다 L1이 있으면 같은 주소의 사본이 여러 곳에 생긴다. 한 코어가 쓰는 동안 다른 코어가 낡은 사본을 읽으면 안 된다. 이를 지키는 규칙이 캐시 일관성(coherence)이다. TileLink는 라인마다 권한 상태를 둔다. DCache의 meta 배열이 이 상태(Meta.coh: ClientMetadata, meta/AsynchronousMetaArray.scala:24-26)를 들고 있고, s1의 hit 판정이 "권한까지 맞는가"를 보는 이유가 이것이다.

L2는 inclusive여야 한다(require(inclusive, "L2 must be inclusive"), Configs.scala:333). L1D에 있는 라인은 반드시 L2에도 있으므로, L2만 보면 누가 사본을 가졌는지 안다. L2는 L1D 몫으로 bank당 128 set × 6 way의 디렉터리 설정을 받는다(sets = 2 × 256 / 4, ways = 4 + 2, Configs.scala:347-348). 디렉터리 동작 자체는 L2 소스가 없어 확인하지 못했다. L2가 보낸 Probe는 8칸 ProbeQueue(Configs.scala:309)가 받아 MainPipe 최우선 입력으로 넣는다. L2와 L3 사이는 CHI 패킷 프로토콜이다(L2Top.scala:233, 368).

가상 메모리와 TLB

프로그램이 쓰는 주소는 가상주소다. 운영체제가 관리하는 페이지 테이블(page table)이 4KB 페이지 단위로 가상주소를 물리주소로 바꾼다. 테이블은 트리라서 VPN을 9비트씩 잘라 단계마다 PTE 하나(8바이트)를 메모리에서 읽는다. Sv39는 3단계, Sv48은 4단계다. KMHv3는 Sv48과 H 확장을 켠다(EnableSv48 = true, HasHExtension = true, Parameters.scala:78, 60). satp.mode 8이 Sv39, 9가 Sv48이다(MMUConst.scala:192-193).

load마다 메모리를 4번 더 읽을 수는 없다. 최근 번역 결과를 담는 작은 캐시가 TLB(Translation Lookaside Buffer)다. KMHv3의 L1 TLB는 모두 48엔트리 완전연관이다(NWays = 48, NSets = 1, Parameters.scala:218-275; 2023-09-14 f9ac118cd, #2289). 엔트리 하나는 연속한 가상 페이지 8개를 담는 섹터다(tlbcontiguous = 8, MMUConst.scala:167). 모두 4KB 페이지로 꽉 차면 48 × 8 × 4KB = 1.5MB를 덮는다(계산). DTLB는 load용(포트 4), store용(포트 2), 프리페치용(포트 3) 세 개이고(mem/MemBlock.scala:654-656), ITLB는 1개다. 응답은 요청 다음 사이클이다(TLB.scala:41; TLBStorage.scala:125).

SMS: 페이지 안의 공간 패턴

SMS는 1KB 구역마다 접근한 라인 모양을 기억했다가 같은 PC·오프셋으로 다시 시작하면 그 모양대로 L2에 요청한다(PHT 64엔트리·2way, SMSPrefetcher.scala:42-57). 활성 생성 표(AGT)에서 접근 수가 문턱을 넘은 구역은 바로 ±30블록 앞을 요청한다. 조건은 access_cnt > act_threshold(SMSPrefetcher.scala:485)이고 문턱 12와 거리 30은 CSR spfctl 리셋값이다(backend/fu/NewCSR/CSRCustom.scala:142-148; PrefetcherWrapper.scala:177-178). SMS 안의 자체 stride 기능은 꺼져 있다(pf.io_stride_en := false.B, :179).

핵심 정리

  1. DefaultConfig의 계층은 L1D 64KB 4-way, L2 2MB 8-way 4 bank(inclusive), L3 OpenLLC 32MB 16-way다. L1↔L2는 TileLink, L2↔L3는 CHI다. 층별 hit 지연은 이 저장소에 없다.
  2. DCache set 8비트 = vaddr[47:12]를 2비트씩 XOR한 값 ∥ vaddr[11:6]이다. 위 2비트가 페이지 밖이라 alias가 생기고, 그 값을 L2에 실어 보낸다(2026-07-03, #6166).
  3. hit는 s1의 tag+권한 판정, 데이터는 s2다. 같은 bank·다른 set인 load는 가장 오래된 하나만 통과한다. miss는 16개 MSHR에 들어가 merge·reject 규칙을 따른다.
  4. MainPipe가 유일한 쓰기 경로이며 victim은 PLRU 결과 그대로(빈 way 우선 없음)다. Dirty victim과 Probe 응답은 WritebackQueue가 L2로 보낸다.
  5. L1 TLB는 48엔트리 완전연관 섹터(8페이지) 구조다. L2TLB는 레벨별 캐시와 PTW 1개·LLPTW 6개로 걷고, A/D 갱신은 page fault로 OS에 맡긴다.
  6. Stride는 갱신 전 conf ≥ 3(여섯 번째 접근), Stream은 구역 라인 12개, SMS는 접근 수 > 12에서 요청을 낸다.

확인 퀴즈

KMHv3 DCache set index의 위 2비트가 만드는 문제는 무엇인가?
256 set × 64B = 16KB라 index가 4KB 페이지 밖 2비트를 쓴다. 가상주소가 달라도 물리주소가 같을 수 있으니 같은 라인이 두 set에 들어갈 위험이 있다. bank는 vaddr[5:1]로 정해져 set과 무관하고, TLB miss는 번역 문제이며, write-back 여부와도 관계없다.
같은 사이클에 P0는 bank 0-3·set 5, P1은 bank 2-5·set 5, P2는 bank 8-11·set 9를 읽는다. 결과는?
P0와 P1은 bank가 겹치지만 같은 set이라 같은 SRAM 행을 함께 읽는다. 충돌 조건에는 set이 다르다는 항이 있다(BankedDataArray.scala:740-750). P2는 bank가 겹치지 않는다. 그래서 나이를 비교할 일 자체가 없다.
A=1, D=0인 PTE가 가리키는 페이지에 store를 하면 KMHv3는 어떻게 하는가?
perm_check의 stUpdate = (!a || !d) && isSt(TLB.scala:463)가 page fault를 만든다. 주석이 "update A/D through exception"이다. 하드웨어가 PTE를 고치는 방식이 아니고, 무시하면 OS가 Dirty 페이지를 모른다. 다시 읽어도 D는 0 그대로다.
같은 PC의 load가 64바이트 간격으로 계속 miss한다. Stride 프리페처는?
Δ=64이면 Δ>>6 = 1이라 stride_valid가 거짓이다(L1StridePrefetcher.scala:108). 신뢰도가 오르지 않으니 몇 번째든 요청이 없다. 여섯 번째는 간격이 128B 이상일 때의 답이고, L2 요청도 같은 발행 조건을 거친다. 이런 촘촘한 순차 접근은 Stream이 맡는다.
MSHR에 블록 X의 load miss가 있고 데이터 첫 beat가 이미 도착했다. 같은 블록 X의 새 load miss는?
load merge는 데이터 첫 beat 전(data_not_refilled)에만 된다(MissQueue.scala:868-871). 그 뒤 같은 블록은 should_reject로 거절된다. 같은 블록에 MSHR을 둘 쓰면 라인이 두 벌 생길 수 있어 새로 할당하지 않는다. 프리페치 칸 규칙은 새 할당에만 해당한다.
